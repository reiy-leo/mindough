## 2026-11-05：心情河流

Rei 2026-11-05 看了第七、八版稿（`work/mood-river/mock7.html`、`mock8.html`）后定下来：左栏活动图下面的心情条形列表换成「心情河流」。下面「Feed 流」第 4、6 条和待确认第 3 条讲心情列表的地方，以这一节为准。

### 规则

1. **位置和样子**：活动图下面，占满左栏剩下的高度（窗口越高，河越长；手机上固定 190px 高）。整块是流动的渐变，没有月份刻度，没有圆角硬边：四边用噪声加 smooth-min 距离慢慢淡出，像水洇开；数据变了，边形也跟着变。
2. **从上往下是时间**：一行一天，最上面最近，往下越来越早。
3. **颜色怎么来**：每一行的颜色由附近几天各心情的条数加权混出来（高斯，宽约 3 天）。一种心情一股水流，写得越多，它的颜色占的面积越大；每股沿自己的路线左右摆。颜色从现有的心情配色（皮肤令牌 `--mood-*`）取色相，深浅另定（2026-11-13 改，见下面「浅色要浅，深色不发黑」）。没选心情的条目算一股中性灰。
4. **没写的日子**：用前后最近写过的两天按距离过渡；最前、最后几天没写，照抄最近写过的那天。
5. **一条都没有**：范围里一条日记都没有时，画一团很淡的中性灰雾（浅色接近背景，深色是深灰），照样呼吸，中间一行「写下第一篇日记，这里就有颜色了」。下面不显示胶囊。
6. **呼吸**：约 6 秒一呼一吸，透明度在 80%–100% 之间起落，亮度 ±4%，边缘伸缩 ±6px，几股颜色缓慢左右漂。系统开了「减少动态效果」就停在静止画面。
7. **范围**：默认最近 30 天（最上面今天）。右上角按钮「最近 30 天 ⌄」，点开是年份（左右箭头翻）和 12 个月；没写过日记的月份灰掉、不能点；能翻到的年份是最早一条那年到今年。选了某个月，河里只画那个月（最上面是月底，往下到 1 号；本月只画到今天），按钮写「2026年10月」。底部「最近 30 天」回默认。范围只记在这一页上，离开日记页再回来是最近 30 天。
8. **心情胶囊**：河流下面一排，心情图标 + 名字 + 条数，按条数从多到少，只列这段时间用过的；数字跟着范围变。点一个按心情筛日记（和以前一样，能和选中某天叠加，活动图也只画这个心情），河里这种颜色更浓，其他变淡；再点取消。筛着的心情在新范围里没有时，留一个 0 的胶囊，好点掉。
9. **提示**：鼠标停在河上某处，或手指点一下，显示那天的「10月12日 · 焦虑 2 条、开心 1 条」，没写的「10月13日 · 没写」；手指点的 2.5 秒后消失。
10. **三皮肤**：月份弹层 Apple 是半透明大圆角、选中月份强调色圆角块；WinUI 方角、「最近 30 天」是描边按钮；Material 3 大圆角容器、月份是胶囊、「最近 30 天」是 tonal 按钮。手机上弹层从底部出来，格子至少 44px 高。

### 浅色要浅，深色不发黑（2026-11-13）

Rei 2026-11-13：「日记中的渐变颜色块的研发发黑，light theme要浅，dark theme深一点」（「研发」是笔误，说的是颜色）。

- **为什么发黑**：心情令牌是给小脸和文字用的，浅色主题里要在白底上看得清，本来就深（Apple `#b07f00`、`#2e7cf6`）；以前河流只往白靠 22%，大块铺开就是一片深色。素净档的心情色是 `#1d1d1f`–`#838388` 的深灰，河流几乎是黑的。
- **现在**：只留令牌的色相，亮度挪到固定一段（OKLab L），色度乘一下再封顶（`riverTone`，core `toneOklab`）：
  - 浅色：L 0.80–0.90，淡彩。比如 Apple 开心 `#f4d59f`、难过 `#b7daff`、生气 `#ffc3b8`；素净档是 `#c4c4c6` 上下的浅灰。正文色压在上面对比度都在 10:1 以上。
  - 深色：L 0.48–0.56，深但不黑，看得出是什么颜色。比如 Apple 开心 `#826c01`、难过 `#3666a2`、平静 `#007587`；浅色正文压在上面 4.6:1 以上。深色透明度上限从 225 提到 240，免得再被深底压暗。
  - 令牌原来越深，河里也稍深一点，所以素净档几股灰的深浅次序不变，还分得开。
- 点了胶囊：那股浅色再深 0.05、深色再亮 0.04，色度放宽一点；别的照旧往背景靠。
- 读令牌颜色时，浏览器认不出的写法（老 WebView 不认 `color-mix`）用内置备用色，不再读成黑色。悬停提示底色也先垫一层实色。

### 怎么画（性能）

- 纯逻辑在 core `mood-river.ts`：`riverDays`（画哪几天）、`riverData`（每天每种心情几条）、`fillRiverGaps`（没写的日子）、`riverProfile`（每行像素各股份量，含胶囊点中的那股加重）、`riverMonths` / `riverYears`（月份选择器）、`riverSeed`（边形随数据变）。
- 像素在客户端 `lib/mood-river-paint.ts`：低分辨率画布（桌面 1 格 = 4px，手机 5px）逐像素算颜色和透明度，CSS 放大成平滑渐变。每行的份量只在数据、尺寸变时算一次，每帧只算横向高斯和软边噪声。
- 动画约 15 帧（requestAnimationFrame 里每 66ms 画一次）；页面切到后台（`visibilitychange`）、河流滚出视口（IntersectionObserver）就停。
- 组件 `components/journal/MoodRiver.tsx`（MoodRiver、RiverRangePicker、MoodChips），替掉了 `MoodList.tsx`。
- 单测：core `mood-river.test.ts`、client `lib/mood-river-paint.test.ts`。

### 2026-10-29：和任务用同一个编辑器

## 1. 目标与不做的事

**目标**：每天随手写几句，以后能按日子翻。和任务一样：数据先存本机，离线能写，多端同步，能导出成 Markdown。（最初还想写的时候顺手看到「这一天做了什么」，Rei 不要，见第 0 节 Q6。）

**不做**（至少 MVP 不做）：
- 不做社交、分享、公开日记；不做 AI 总结 / 情绪分析。
- 不做标签（Mindough 本来就没有标签，导入时 `#标签` 原样留在文字里，和 EXPORT.md 决定 4 一样）。
- 不做天气、定位、录音、视频（天气要定位 + 联网接口，和「离线能写」冲突；以后再说）。
- 不做端到端加密，不做应用锁（应用锁以后可选，见第 10 节）。
- 日记不是任务：没有状态，不进关系图，不算「可开始 / 还不能开始」，也不进我的一天清单。

## 2. 核心设计（推荐）

1. ~~一天一篇~~ → 2026-10-28 起一天多条（Feed 流，见顶部）。当时的理由：日记本来就按天算；月历、那年今日、导出成 `YYYY-MM-DD.md` 都能一一对上；和 Obsidian 每日笔记是一个结构。一天想记几次，就用工具栏的「插入时间」在光标处插一行 `**14:30**`，不拆成多条。
   - 「一天多条」（Day One 那样）：每条一行，同步不会冲突；但月历要汇总，导出要拆多个文件，列表也碎。麻烦比好处多，不推荐。
2. **id 由日期算出**（和 `taskLinkId` / `prefId` 一个做法）：两台设备离线各自打开「今天」那篇，同步后还是同一行，不会冒出两篇 10-17。删了再写同一天，也是同一个 id（把墓碑翻回来）。
3. **内容 = markdown**（编辑器 2026-10-25 起是 Tiptap），和任务内容同一个编辑器（标题、清单、提示块、公式、折叠块…都能用；2026-10-25 起没有工具栏，靠快捷键和手打写法）；插图走现有的上传（登录并联网时进 R2，离线时存 data:）；网上的图片也只显示成文字（PRODUCT 第 12 条）。
4. ~~「这一天」只读侧栏~~ → Rei 2026-10-17：「这一天」汇总不放在日记中。J1 不做侧栏，也不给「插入」（只读显示留作待问）。
5. **可选字段只留「心情」一个**（12 个动画图标，可不填；Rei 2026-10-17 说 5 个太少）。不做标签、天气、地点。
6. **入口**：侧边栏「今天」小节加「日记」；我的一天页底部一张「今天的日记」小卡（没写时「写几句今天的事」，写了显示第一行）。
7. **同步还是整段比、后写的赢，但日记多一道保护**：两台设备都改了同一天、内容又不一样时，不悄悄丢掉一边，而是把输的那版收进末尾的折叠块「另一台设备上同时写的」。等 M5 的正文逐字合并做好，日记直接用它，这道保护就去掉。
8. **导出成 `journal/YYYY/MM/YYYY-MM-DD.md`**，front matter 只放 id、date、mood；导回来时按 id 认。

## 9. 同步与冲突

- 新表 `journal_entry` 走现有 outbox + 游标 + 行级 LWW，云端不用改（云端只存整行 JSON）。
- **整段后写赢的问题**：任务内容让人覆盖了还能重写，日记覆盖了就没了。所以 MVP 给日记单独加一道保护：
  - `applyRemote` 收到一篇日记时，如果本机这一行还在 outbox 里没推（本机也改过），而且两边内容不同，就不直接取赢家，而是 **赢家内容 + 末尾一个折叠块**：`<details><summary>另一台设备上同时写的 · 10-17 14:30</summary>…输家内容…</details>`，当成一次新写入（新 HLC）推上去。已经有的段落不重复（照 `merge.ts` 里 `mergeNotes` 的思路），两台同时合，结果也一致。
  - 心情字段照常 LWW（丢了能再点）。
  - 这道保护只在「两边都离线改了同一天」时才起作用，平时只在一台设备上写，碰不到。
- **和 M5 的衔接**：M5「正文逐字合并（CRDT）」做好后，任务和日记的内容一起换过去，上面的保护去掉。`body_md` 用同一个列名，就是为了到时少改。
- 不建议现在就给日记单独上 CRDT：工作量差不多是把 M5 提前做一半，而日记基本只在一台设备上写。

1. **一天一篇还是一天多条？** 推荐 **一天一篇**（+「插入时间」）。理由见第 2 节第 1 条。
2. **英文名？** 推荐 **Journal**（Apple Journal、Day One 都这么叫；Diary 偏「私密日记本」、口气幼一点）。代码 / 路由 / 深链 / 导出文件夹统一用 `journal`。（任务里写的 `diary/…` 也可以，选定一个全处统一。）
3. **入口放哪？** 推荐侧边栏「今天」小节最后 + 我的一天底部小卡；**手机标签栏不动**，日记在「更多」里。备选：用「日记」换掉手机标签栏的「列表」。
4. **可选字段？** 推荐 **只要心情**（5 档）。要不要天气 / 地点 / 标签？推荐都不要。
5. **凌晨写算哪天？** 推荐 **按 0 点分**，但 0–4 点打开日记时顶部提示「还在写昨天的？」一键切到昨天那篇。备选：设一个「一天从几点开始」（默认 4 点），整个日记都按它算。
6. **「这一天」汇总放哪些？** 推荐：完成 / 关闭的任务 + 打卡 + 新加的资料；都只显示、不写进日记。要不要「插入」把它们一键变成文字列表？推荐只给单行「插入」，不给「全部插入」（免得日记变流水账）。
7. **同步保护**：推荐 MVP 就做「两边都改时保留另一版到折叠块」，M5 再换成逐字合并。备选：完全按整段后写赢（会丢字）。
8. **导出文件夹** `journal/YYYY/MM/YYYY-MM-DD.md`，推荐按年 / 月分两层（Obsidian 里好翻）；备选平铺 `journal/YYYY-MM-DD.md`。
9. **隐私**：推荐 J3 只做三个开关（搜索里不显示、我的一天不显示预览、导出含不含）；应用锁等 Rei 说要再做。
10. **提醒**：默认关，推荐默认时间 21:00；当天写过就不响。
11. **将来的日子能不能写？** 推荐能写（当计划 / 备忘也行），月历上照常显示。备选：只能写今天和以前。

## 14. 数据表与迁移（J1 实际做的）

SQLite 迁移 **v6**（动工前确认过 main 和各分支都没用 v6）：

```sql
CREATE TABLE IF NOT EXISTS "journal_entry" (
  "id" TEXT PRIMARY KEY NOT NULL, "updated_at" TEXT NOT NULL, "deleted" INTEGER NOT NULL DEFAULT 0,
  "date" TEXT NOT NULL,              -- 本地日期 YYYY-MM-DD（按「一天从几点开始」算的那天）
  "body_md" TEXT NOT NULL DEFAULT '',
  "mood" TEXT,                       -- 心情英文 id（happy…），可空
  "base_at" TEXT,                    -- 同步保护：这一版是在哪一版「别的设备写的」内容上改的
  "created_at" TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS "journal_entry_date" ON "journal_entry" ("date");
```

- `types.ts` 的 `JournalEntry`，`COLUMNS.journal_entry = { date: 'text', body_md: 'text', mood: 'text?', base_at: 'text?', created_at: 'text' }`。
- id：`journalEntryId(date)`——UUIDv7 形状，时间戳段 = 这一天 00:00 UTC 的毫秒数，第三段 `7000`、第四段 `8002`，其余为 0；各设备算出来一样。
- pref 键（跟账户同步）：`journal.day_start`（0–23，默认 5）、`journal.remind`（默认开）、`journal.remind_time`（默认 21:00）。
- 云端不用改（只存整行 JSON）。旧版客户端拉到 `journal_entry` 的行会忽略，不影响别的。
- core `journal.ts`：`journalEntryId`、`isDateKey`、`journalToday`、`canWriteJournal`、`MOOD_IDS` / `moods()` / `moodLabel`、`journalWordCount` / `journalPreview`、`isJournalConflict` / `mergeJournalConflict` / `splitConflictBlocks` / `conflictSummary`、`monthGrid` / `addMonths` / `journalOfMonth`。Store：`journalDayStart()`、`journalToday()`、`journalOf(date)`、`setJournal(date, { body_md?, mood? })`、`deleteJournal(date)`、`journalBaseOf(id)`。

**同步保护怎么判断「没看到对方那版」**：

- 本机每次写：上一版是别的设备写的，`base_at` 就记上一版的 `updated_at`；上一版是自己写的，就沿用它的 `base_at`。
- 拉下来一版 R，满足这几条就说明 R 没看到本机这版 L：R 比 L 新、正文不同、L 不空，而且 `R.base_at` 为空或早于 `L.updated_at`。
- 这时取 R 的内容，末尾加折叠块收着 L 里 R 没有的段落，`base_at = R.updated_at`，当成本机的新写入推上去。
- 只有输的那台设备会合并（HLC 是全序）。合好的那版，在别的设备看来 `base_at` 就是它手里的 R，不会再合。比较内容时忽略空白和 markdown 记号，已有的段落不重复，所以几台设备各合一次，结果也一致。
- 删除（墓碑）不触发保护。
